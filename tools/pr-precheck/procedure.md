# Procedure: how this tool grades a PR package

## Read order

Read the yardstick before the thing graded: issue and plan first, then the diff, then the words that describe the diff, then the proof. The side-by-side checks only work if you know what the PR was supposed to do before you see what it says it did.

1. Identify the mode. If live, read `scope.md` first (before any file or command): refuse and stop if the PR or branch targets a repo other than the `Repo:` line, and stop without grading if that line is an unfilled placeholder, telling the student to fill it with their section's Path Review repo. If eval, ignore `scope.md` and `voice-guide.md`, and use only the bundle.
2. Read `rubric.md` and `references/evidence-guide.md`. If the rubric has no checks or this procedure has no steps, stop and say so. In live mode, also read `voice-guide.md`.
3. Read the issue: the reported symptom, the trigger, the expected behavior, the issue number, and any maintainer directions in the thread. Note the issue number; you will compare it to the description later. (Eval: the Issue and Thread highlights sections. Live: the real issue thread and linked reproduction; house-chain students use the house repro pack.)
4. Read the plan, including its deviation notes: the scope and not-in-scope list, the named files, the steps, the original repro evidence, and the test plan. Write down the list of planned files and steps, the list of recorded deviations (what changed, and why), and the list of planned tests. (Eval: Plan context. Live: `plan.md`, or the house plan.)
5. Read the repo's stated asks: the PR template sections, the contribution policy, the AI-use policy, and the required checks. Write down each ask as a short line. (Eval: Repo facts. Live: fetch the PR template and `docs/CONTRIBUTING.md`; if one cannot be fetched, record it as inaccessible, not absent.)
6. Only now read the diff. Write down every changed file path and, per file, what its hunks do in one phrase. (Eval: the candidate PR's Diff. Live: `git diff main...HEAD`.) In live mode also read the commit list (`git log main..HEAD`) and `git status`, and record which edits are committed and which are uncommitted or untracked.
7. Read the draft title and description. List each factual claim: what changed, why, the issue reference, what was tested, and what passed. (Eval: Title and Description. Live: `pr_draft.md`.)
8. Read the test evidence last. List each command or manual step, what was observed, and its outcome. (Eval: Test evidence. Live: `test_evidence.md`.) Do not grade anything until all of the above has been read.

## Evidence gathering

Gather per check, using the entry of the same name in `references/evidence-guide.md`. Record, for each check, one deciding fact or quote and exactly what is absent if something is missing.

- **plan-fidelity** (evidence guide: Plan fidelity). First sort the plan's steps into implementation changes (edits to code, tests, docs, config) and verification or investigation steps (run, check, confirm). Put the diff file list beside the implementation changes and the plan's file list. For each changed hunk, mark it as: planned implementation change, necessary supporting edit, recorded deviation, or uncovered. For each planned implementation change, mark it as: in the diff, explained by a recorded deviation, or absent. For each verification or investigation step, find its recorded evidence in the test evidence and mark it: evidenced, explained by a recorded deviation, or neither; do not look for these steps in the diff. Note any hunk touching an originally not-in-scope item or any dropped planned work, and whether a recorded deviation covers it and the description states it. Unrelated hunks go to diff-reviewable. Then read the description's account of scope and mark whether it agrees with the diff, in both directions (does not claim work that is absent, does not hide work that is present).
- **description-accurate** (evidence guide: Plan fidelity, description claims). For each claim listed in Read order step 7, find its support: a hunk in the diff for "what changed", the issue text for "why", the issue number for the reference, a recorded outcome in the test evidence for any "fixes", "resolves", or "passes" claim. Mark each claim supported, unsupported, or contradicted. Check that the title says what the diff does. Mark any statement that CI or a check passes against whether that outcome is recorded; CI that has not run counts as pending.
- **repro-evidence** (evidence guide: Test evidence). Pair the original reproduction (trigger, inputs, observed symptom) with the recorded before and after steps and the plan's test plan. Record: is the trigger the same, does the run go through the changed code, is the before-observation shown, is the after-observation shown, and does the after-observation support what the description claims. Mark each planned test as present, absent with an explanation, or absent without one. Mark each test as live, manual, or mocked. Record whether the description or plan deviations disclose any partial result, and whether the evidence shows exactly what improved and what remains. Provenance: in live mode, compare the code that was tested (files and state the output came from, `git status`) with the committed diff. Evidence captured before the commit is usable when the tested code matches the submitted code; record any actual difference and whether it is material to the behavior tested, and do not discount evidence only because it predates the commit.
- **repo-checks** (evidence guide: Test evidence, repository checks). Build the list of required checks (from the repo's stated requirements, plus on live Path Review the four commands `make test-unit`, `make test-integration`, `make lint`, `make typecheck`) and planned relevant checks (from the plan's test plan). For each, find the command, the attempt, and the actual outcome in the test evidence and classify it: passed, failed, blocked, skipped, not run, or missing. For failed, blocked, skipped, and not run, record the concrete evidence offered: quoted error output for a blocker, base-branch results for an unrelated failure, repo facts for inapplicability. A stated reason with no such evidence, or a reason of lack of time, inconvenience, or assuming another test covers it, is recorded as no valid exception. Separate local checks (which should already have been attempted) from CI that cannot run until the PR is opened (pending). Compare against the description for any misreported result. If a blocked or skipped check touches an explicit repository requirement or prohibition, note it for repo-standards. If the bundle states no full-suite requirement, add none.
- **diff-reviewable** (evidence guide: Diff quality). Walk the diff hunk by hunk and the file list once, looking for debug leftovers, dead or commented-out code, unrelated edits (formatting churn, drive-by refactors, unrelated files), and accidental draft or scratch files. Check the commit list for commits that only add and remove such material. In live mode, check `git status` for stray files and note any that are committed.
- **repo-standards** (evidence guide: Standards and comms). Pair each ask recorded in Read order step 5 with the place the PR honors it: each template section against the description's section, the contribution-policy asks against the title, description, and diff, the AI-use disclosure against the description (live course PRs: Notes for Reviewers, specific), and each explicit maintainer direction in the thread against what the PR does. Mark a section blank, boilerplate, or removed as a miss. Mark N/A only if it carries a reason. If a documented deviation is offered for an explicit prohibition, record that it does not waive it. If no template, policy, or direction is stated, record "none stated" and do not invent one.

## Check execution

1. Execute the checks in rubric order: plan-fidelity, description-accurate, repro-evidence, repo-checks, diff-reviewable, repo-standards. Grade every check, including after an earlier failure; a failure never skips a later check.
2. For each check, apply the rubric's pass condition to the gathered evidence. Grade `pass` when the pass condition is supported by evidence you can name. Grade `fail` when the evidence demonstrates a contradiction or a missing required element (for example, a hunk the plan does not cover, a "fixes" claim with a failing after-run, a required check with no recorded outcome). Grade `unclear` only when the evidence the check needs is genuinely unavailable (for example, a policy page that cannot be fetched) or ambiguous (two readings of the same line lead to different grades).
3. Before grading `unclear`, revisit that check's evidence location once. In live mode, report access failures as such; never read an inaccessible policy as no policy. In eval mode, never fetch; if the bundle lacks the fact, the check is graded on what the bundle contains: absence of a required element is `fail`, while a stated but unreadable ask is `unclear`.
4. Judge the outcome, not the write-up. A terse description or a manual test can pass; a long, confident one can fail. Ignore the length, headings, and the number of files, commits, or lines.
5. Treat a narrower result, a manual check, an attempted check with an evidenced environment blocker, and a disclosed partial result as the rubric describes them: each can pass when the evidence and the deviations and description record it accurately, and none is graded as a failure just for being less than everything. Disclosure never replaces running a required check, and a skipped or not-run check passes only on concrete evidence of impossibility or inapplicability, as the rubric states. Apply only the fail conditions written in the rubric; do not add fail conditions from this procedure or the evidence guide.
6. A check may be graded from the notes already gathered if they contain its deciding fact. Re-read the package only to resolve a concrete ambiguity, not to re-grade a settled check.
7. Do not add a requirement the rubric does not contain. If a step you need is not written here, report it as a procedure gap in the summary and continue with the rubric as written.
8. In live mode, separately compare the draft title and description against `voice-guide.md` and list any rule broken, quoting the rule and the offending words. Do not change a check's grade because of it; a check changes only if its own pass condition reads the same fact.

## Verdict assembly

1. List all six checks in rubric order, each with its grade (pass, fail, or unclear) and one deciding fact or quote.
2. Apply the rubric's verdict rule exactly: `accept` only if all six required checks are `pass`; if any check is `fail` or `unclear`, the verdict is `reject`. Do not soften, round up, or replace the rule with an overall impression.
3. When the verdict is `reject`, choose the primary rejection reason by one rule: the first check in rubric order graded `fail`; if no check is `fail`, the first check in rubric order graded `unclear`. Name it in the summary and quote its deciding fact. Still report every other non-passing check in its own line.
4. In live mode, add after the per-check lines: voice-guide notes, uncommitted or untracked work, inaccessible evidence, and procedure gaps. These do not change the verdict.
5. End the reply with the fenced JSON block from SKILL.md: `item` (PR URL or bundle id; live with no PR yet, the repo, issue number, and branch), all six checks in rubric order with `name`, `grade`, and a one-line `evidence`, then `verdict`. The block must be valid and last, with nothing after it.
