# Rubric: is this pull request ready to submit?

## Checks

Six required checks, graded in this order. Evidence locations are in `references/evidence-guide.md` under the family named in each row. "Live" and "eval" locations are given there.

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | The plan's steps, split into implementation changes (edits to code, tests, docs, or config) and verification or investigation steps (run, check, confirm), compared with every recorded deviation (live: `plan.md`; eval: Plan context). Implementation changes are compared with the diff's changed files and hunks (live: `git diff main...HEAD`; eval: the candidate PR's Diff); verification and investigation steps are compared with their recorded evidence in the test evidence. The description's account of scope is read against both; see Plan fidelity | Pass if every implementation change in the diff falls inside the plan plus its recorded deviations (supporting tests and edits the planned change needs are inside), every planned implementation change either appears in the diff or is accounted for by a recorded deviation that the description states accurately, and every planned verification or investigation step has recorded evidence or a recorded deviation explaining its absence (such steps are not expected to appear in the diff). A change to the original scope passes when a recorded deviation explains it and the description states it accurately: work the plan originally listed as out of scope, or planned work dropped, is not an automatic failure after a justified, recorded revision. A narrower result passes on the same terms. Fail if the diff does substantive implementation work that neither the plan nor a deviation covers, planned implementation work is missing while the description is silent about it or implies it was delivered, a planned verification or investigation step has neither evidence nor an explanation, or the description's account of scope contradicts the diff in either direction. Unrelated work that does not serve the issue is graded under diff-reviewable, not excused here. | required |
| description-accurate | The PR title and description compared with the diff, the issue, and the observed results in the test evidence; see Plan fidelity (description claims) and Test evidence for the results | Pass if the title and description name the correct issue (the one the plan belongs to), explain accurately what changed and why in terms the diff supports, and make no claim stronger than the observed results: any claim of a complete fix, of resolving the issue, or of checks passing is backed by recorded outcomes, and known limits or remaining failures are stated. A terse description can pass. Fail if the issue reference is missing or wrong, the description describes changes not in the diff or omits a major part of the diff, claims a complete fix the evidence does not show, claims passing checks without recorded results, or describes pending CI as passed. | required |
| repro-evidence | The test evidence's recorded before and after commands or manual steps and their observations compared with the issue's original reproduction and the plan's test plan; the code that was tested compared with the submitted diff; see Test evidence | Pass if the evidence can distinguish the claimed improvement from the original failure: it exercises the affected behavior (the reproduced trigger, run through the changed code), records what was observed before and after (or says why a before-state could not be recreated), and the after-observation supports exactly what the PR claims and no more. Manual checks count. Mocked or stubbed tests are identified as mocked and are not presented as live verification; a claim about live behavior needs a live observation. Each planned test is present or its omission is explained. A disclosed partial result passes when the evidence shows exactly what improved and what remains, and the plan's deviations and the description record that limit accurately; disclosure alone never replaces running the relevant checks. Results captured before the commit, while changes were uncommitted, are usable when the tested code matches the submitted code; grade against a difference only when one is identified and material to the behavior tested. Fail if the evidence does not exercise the relevant behavior, is only an assertion, could not tell a fixed result from an unfixed one, presents mocked results as live, rests on tested code that materially differs from the submitted diff, or the PR claims a fix the evidence does not demonstrate (including an after-run that still shows the failure the PR calls fixed). | required |
| repo-checks | The commands, attempts, and actual outcomes recorded in the test evidence for each check the repository requires and each relevant check in the plan's test plan (live: also the CONTRIBUTING and PR template asks; eval: the repo facts); see Test evidence (repository checks) | Pass if each required or planned relevant check has an identifiable command, an actual attempt, and a recorded outcome (passed, failed, or blocked), and none is misreported. A check recorded as skipped or not run does not pass on a stated reason alone: it passes only when concrete evidence establishes why execution is impossible (for example quoted error output from an attempt) or why the check does not apply (for example repo facts showing it does not cover the changed files). Lack of time, inconvenience, or an assumption that another test covers it are not valid exceptions. An attempted check with an evidenced environment blocker passes this check when reported accurately; whether an explicit repository prohibition or requirement still bars the PR is decided under repo-standards, not here. A failure passes only when shown to be unrelated to the change (for example, the same failure recorded on the base branch). Local checks that should already have been attempted are graded as above; CI that cannot run until the PR is opened is pending, must be described as pending, and is never counted as passed. In live mode on Path Review the required checks are `make test-unit`, `make test-integration`, `make lint`, and `make typecheck`. Do not require a full test suite unless the repo facts or plan state one. Fail if a required or planned check has no command, attempt, or outcome ("tests pass" alone), failed because of the change, was skipped or not run without concrete evidence of impossibility or inapplicability, or is reported as passed without a recorded result. | required |
| diff-reviewable | The unified diff and the commit list (live: `git diff main...HEAD`, `git log main..HEAD`, `git status`; eval: the candidate PR's Diff and Commits); see Diff quality | Pass if the committed change is one bounded change serving the issue, including the supporting tests it needs, and contains no debug leftovers (stray prints, temporary logging, debugger statements), dead or commented-out code, unrelated edits (drive-by refactors, formatting churn outside the touched lines, unrelated files), or accidental draft or scratch files (plan, PR draft, notes, logs, backup files). Judge what the change is, never how many files, commits, or lines it has. Fail if any such debris or unrelated hunk is present in the committed change. | required |
| repo-standards | The repository's stated asks compared with the PR description and its filled sections: PR template, contribution policy, AI-use rules, and explicit maintainer directions (live: the template, `docs/CONTRIBUTING.md`, the issue thread, and the scope's house rules; eval: the repo facts and thread highlights); see Standards and comms | Pass if every ask that applies is met with real content: each template section is filled or carries a meaningful N/A explanation, contributor-policy asks are followed, an AI-use disclosure is present wherever the policy requires one, and explicit maintainer directions in the thread are honored. In live mode a course PR must disclose AI assistance in Notes for Reviewers, specifically (which tool, used for what, what the author verified). A documented deviation does not waive an explicit prohibition. Do not invent policies: if the repo states no template, policy, or direction, there is nothing to fail. Fail if a required section is blank, boilerplate, or removed, a required disclosure is missing, or an explicit prohibition or maintainer direction is contradicted or ignored. | required |

## Verdict rule

Accept only if every required check passes. Any required check graded fail or unclear means reject. Grade `unclear` only when the evidence a check needs is genuinely unavailable or ambiguous after re-reading its evidence location; `unclear` counts the same as `fail` for the verdict. Preferred checks, if any are ever added, never change the verdict. Grade every check even when an earlier check fails. A PR that honestly discloses a shortfall can pass every check; "less than everything" is never by itself a reason to reject.
